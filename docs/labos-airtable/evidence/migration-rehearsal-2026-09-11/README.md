## What the rehearsal does

It builds the pre-migration production shape, seeds it, and walks the whole chain **forward and then all
the way back**, with rows in the tables at every step. The two migrations that rewrite existing data are
the reason it exists rather than a unit test:

- `e5f3a71c8d92` normalises `labos_test_id` across three historical formats and *then* constrains the
  result. Either ordering error is invisible against an empty database.
- `c7e4a2b81f56` splits existing impact attempts one-per-impact and renumbers them under a uniqueness
  constraint that the renumbering itself can violate.

## The deployment head, added to the chain on 2026-09-11

`a4f18c2d3b90` was previously rehearsed alone. It is now the last link of this chain, so it runs against a
database that already holds the split impact shape **with rows in it** — the shape the node will be in.
A migration that has only ever met an empty table has not been rehearsed.

What the new checks assert:

- all three columns exist and are **nullable**. A `NOT NULL` here is unsatisfiable for historical rows;
- **no backfill** — every pre-existing `missile_impact_tests` row still has `NULL` in `impact_family`,
  `impact_level` *and* `target_velocity` after the upgrade. Nothing may infer a family from the free-text
  `missile` column or a target from historical shot velocities;
- the named CHECK accepts `LMI/D`, `LMI/E` and `SMI/none`, and **refuses `SMI` with a level** — the one
  pairing that can never be meaningful whatever the vocabulary becomes;
- the downgrade removes all three columns **and** the named constraint, leaving the table as it found it.
